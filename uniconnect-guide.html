Uniconnect
from zero to full-stack

A university social + utility platform. 34 use cases. React + TypeScript frontend, Node.js + Express backend, SQLite database. JWT auth. This page breaks down every layer — how it works, where code lives, and where to learn each part.

System architecture

🌐
Browser — React + TypeScript (Vite)
Single-page app. All views are in src/App.tsx (10 sections). Communicates with the backend via src/api.ts which auto-injects the JWT from localStorage on every request.
↓   HTTP JSON  +  Authorization: Bearer <JWT>
⚙️
Server — Node.js + Express.js
Entry at server/index.js. REST API across several route files. JWT verification middleware runs before every protected endpoint, attaching req.user.id to the request.
↓   better-sqlite3  (synchronous — no async/await needed)
🗄️
Database — SQLite via better-sqlite3
Schema defined in server/db.js. Physical file is server/uniconnect.db. 10 tables covering users, study groups, resources, messages, notifications, lost & found, and moderation reports. Seeded via server/seed.js.

⚠ important Two separate package.json files
Root package.json manages the frontend (React, Vite, TypeScript). server/package.json manages the backend (Express, better-sqlite3, jsonwebtoken). They are totally independent. Run npm install in the root for frontend deps, and cd server && npm install for backend deps.
03
Frontend
React + TypeScript — everything in src/
src/api.ts key file
The custom fetch wrapper. Exports api.get(), api.post(), api.put(), api.delete(). Before every request it reads the JWT from localStorage and injects it as an Authorization: Bearer <token> header automatically. No component ever has to manually deal with tokens.

Why this matters: Without it, every single API call across all 34 use cases would need to manually grab the token and set headers. api.ts centralizes that in one place — classic DRY principle.

App.tsx — 10 sections

Every section is separated by a /* ═══ SECTION N — ... ═══ */ comment. Every component has a JSDoc comment mapping it to its UC number. Click any section to expand.

S1Types & interfaces▶
TypeScript type definitions for every entity the frontend deals with: User, Resource, StudyGroup, Message, Notification, LostFound, Report. Think of this as the frontend's own schema — it mirrors the DB tables so TypeScript knows the shape of every API response.
S2Constants & config▶
Static data like subject lists, resource category enums, and default configs. Centralizing these here means if you change a category name, you change it in one place and every dropdown/filter that uses it updates automatically.
S3Shared components▶
Reusable UI pieces used across the whole app: modals, buttons, spinner loaders, notification badge. These are referenced by every section below — change one component here and it updates everywhere.
S4Auth pages — UC 1–3▶
Login and Register views. On successful login: backend returns a JWT → api.ts stores it in localStorage → app redirects to dashboard. On register: same flow, account created first. These are the only pages accessible without a JWT.
S5Dashboard — UC 4–5▶
Main landing screen after login. Makes multiple API calls on mount to aggregate stats (your resources, active borrows, unread notifications, study groups). Renders quick-access cards for each major feature area.
S6Resource sharing — UC 6–13▶
Post, browse, borrow, approve/reject borrow requests, mark returned, and rate resources (books, notes, equipment). Hits /resources and /borrowrequests routes. Binds to Resources → BorrowRequests → Transactions tables in that order.
S7Study partners & groups — UC 14–21▶
Two sub-features: 1-on-1 partner matching (send/accept PartnerRequest) and group management (create, join, leave StudyGroups + GroupMembers). Also handles group chat and session scheduling within a group context.
S8Messaging & notifications — UC 22–26▶
Direct messaging between users (Conversations + Messages tables) and an in-app notification feed (Notifications table). Notifications are created by the server when significant events happen — borrow approved, partner request, new message, etc.
S9Lost & found — UC 27–30▶
Post a lost or found item with location/description, browse all active listings, claim an item, and mark it as resolved. Uses the LostFound table. Simple CRUD, but includes status state machine: open → claimed → resolved.
S10Admin & moderation — UC 31–34▶
Admin-only panel. View and action flagged reports, manage (ban/unban) users, and see an audit log of moderation actions. Protected by both JWT middleware AND a role check (admin only) on the server side. Uses the Reports table.
Styling system — index.css + App.css
No Tailwind, no component library — pure vanilla CSS.
index.css: CSS custom properties (color palette, spacing scale, shadow tokens), typography reset, global base rules.
App.css: Layout utility classes + @keyframes animations. Dark navy/cyan design theme.

Tailwind config exists but is unused — the project was scaffolded with it but the team chose hand-rolled CSS instead.

04
Backend
Node.js + Express — everything in server/
server/index.js entry point
Creates the Express app → registers cors middleware → registers express.json() body parser → mounts all route files under their URL prefixes (e.g. /api/auth, /api/resources) → calls app.listen(PORT). Everything boots from here.

server/routes/ — one file per domain

auth.js
POST /register — hashes password (bcrypt), inserts user, returns JWT.
POST /login — verifies password hash, signs and returns JWT.
users.js
GET/PUT profile, search users by name/subject, update ratings after a borrow transaction.
resources.js
Full CRUD for resources. Also handles borrow requests: create → approve/reject → mark returned. Creates Transactions and triggers Notifications.
groups.js
Create study groups, join by ID, leave, list members. Writes to StudyGroups and GroupMembers.
messages.js
Start a conversation between two users, send a message, list all conversations for current user, read a thread.
lostfound.js
Post / browse / claim / resolve lost-and-found items. Status transitions handled here.
reports.js
Admin only. GET all reports, update status (reviewed/actioned), ban user. Protected by a secondary admin role check beyond just the JWT middleware.

server/middleware/ — JWT guard

auth.js middleware runs before every protected route
Reads the Authorization header → strips "Bearer " prefix → calls jwt.verify(token, SECRET).
If valid: attaches req.user = { id: ... } and calls next() so the route handler runs.
If invalid/expired/missing: immediately responds with 401 Unauthorized — the route never fires.

This is how the backend knows who is making every request. Route handlers use req.user.id to scope queries (e.g. "get resources owned by this user").
server/db.js DB layer
Opens the SQLite connection with better-sqlite3. Contains all CREATE TABLE IF NOT EXISTS statements. They run synchronously at server startup — no async/await needed anywhere in the DB layer, which makes query code much simpler.

Database schema
10 tables in server/db.js · stored in server/uniconnect.db

PK = primary key  ·  FK = foreign key  ·  All tables use SQLite syntax (INTEGER PRIMARY KEY AUTOINCREMENT, TEXT, etc.)

TablePurposeKey columns
UsersStudent accounts, auth, profileidPK, email, password_hash, rating, privacy_prefs, role
StudyGroupsStudy group metadataidPK, name, subject, description, creator_idFK
GroupMembersGroup roster (many-to-many)group_idFK, user_idFK, role (admin/member)
PartnerRequests1-on-1 study buddy matchingidPK, from_userFK, to_userFK, status (pending/accepted/rejected)
ResourcesBooks, notes, equipment listingsidPK, owner_idFK, type, title, availability, condition
BorrowRequestsLending request lifecycleidPK, resource_idFK, borrower_idFK, status, message
TransactionsCompleted borrow exchangesidPK, borrow_request_idFK, borrowed_at, returned_at
ConversationsDM chat threadsidPK, participant_ids (JSON array)
MessagesIndividual chat messagesidPK, conversation_idFK, sender_idFK, body, created_at
NotificationsIn-app alert feedidPK, user_idFK, type, read (bool), payload (JSON)
LostFoundLost & found item listingsidPK, reporter_idFK, status, location, image_url
ReportsModeration flagsidPK, reporter_idFK, target_user_idFK, reason, status
